## Summary

Reviewed the three source files introduced in Phase 04.14: the SQL migration that
establishes the Präsidiums-Admin security boundary, the role-adaptive Leitungs-Seite,
and the updated SELF-HOSTING.md documentation.

The core security design is sound: the Admin JWT carries `is_admin`/`admin_praesidium_id`
and deliberately omits `praesidium_id`/`is_master`, so all existing RLS policies deny
patient/token/checklist raw access. The `argus_is_admin()` function correctly gates on
`argus_token_active()`, the jti instant-revoke applies, and the scoped issue/revoke RPCs
enforce the Präsidium boundary with multiple redundant guards.

Two critical defects were found:

1. `argus_exchange_admin_code` reads `expires_at` from `access_tokens` but never
   validates it, meaning an expired Admin code (with `expires_at` set) can still be
   exchanged for a fresh JWT. Every other exchange RPC in the codebase (0009 version of
   `argus_exchange_code`) includes this check.

2. `argus_exchange_code` (the normal device-code RPC, not part of this migration but
   part of the active system) does NOT reject tokens with `is_admin=true`. An Admin code
   entered in the FIELD APP (index.html) — which only calls `argus_exchange_code` —
   would receive a legitimate device JWT carrying `praesidium_id`, granting full
   read/write access to patients, CCPs, and checklists for that Präsidium via the
   existing RLS policies. This negates the Admin role's intended data isolation.

## Critical Issues

### CR-01: `argus_exchange_admin_code` Does Not Enforce `expires_at` — Expired Admin Codes Remain Exchangeable

**File:** `supabase/migrations/0013_phase414_admin_rolle.sql:104`

**Issue:** The function selects `expires_at` from `access_tokens` (line 104) but never
checks whether the code has expired before issuing a JWT. The 0009-era
`argus_exchange_code` explicitly checks:

```sql
if v_token.expires_at is not null
   and v_token.expires_at <= (extract(epoch from now())*1000)::bigint then
  return jsonb_build_object('error', 'Code abgelaufen');
end if;
```

`argus_token_active()` (rewritten in 0009) does enforce `expires_at` for already-issued
JWTs, but only after a JWT has been obtained. The exchange RPC is the gate at issuance
time. Admin codes are not expected to have `expires_at` set today (no `ttl_hours` default
path sets it), but SELF-HOSTING.md Abschnitt 8 allows creating Admin codes with any
column values, and a future Admin code issued with `expires_at` would be perpetually
exchangeable after it has nominally expired.

**Fix:** Add the same expiry guard present in `argus_exchange_code` (0009), directly
after the `revoked` check:

```sql
if v_token.expires_at is not null
   and v_token.expires_at <= (extract(epoch from now())*1000)::bigint then
  return jsonb_build_object('error', 'Code abgelaufen');
end if;
```

Insert after line 113 (the `revoked` check), before the `is_admin` check.

### CR-02: Admin Code Accepted by `argus_exchange_code` (Normal Device Exchange) — Patient Data Escalation

**File:** `supabase/migrations/0009_paket2_gastcode_schulung.sql` (the live version of
`argus_exchange_code`); the vulnerability is introduced by `0013_phase414_admin_rolle.sql`
adding the `is_admin` column without updating the device exchange RPC to reject it.

**Issue:** `argus_exchange_code` (the field-app exchange RPC, last defined in 0009)
checks for `observer=true` and rejects it with `'Beobachter-Code — nur für die
Lageansicht gültig'`, but has NO equivalent check for `is_admin=true`. An Admin code
entered in the FIELD APP (index.html calls only `argus_exchange_code`) passes all guards
(not observer, not revoked, not expired, not single_use consumed) and receives a JWT
containing:

```json
{ "praesidium_id": "<admin-praesidium-uuid>", "is_master": false, ... }
```

The RLS policies for `patients`, `ccps`, `checklists`, and `access_tokens` (select) all
use `praesidium_id = public.argus_praesidium_id()` as the non-master grant path. A JWT
issued this way grants full read/write access to all patient rows, CCPs, checklists, and
the access_tokens list for that Präsidium — defeating the Admin role's intended
prohibition on patient data access.

The Leitungs-Seite login flow (`doLogin`, line 641–689) does not trigger this path in
normal use because it checks `data.is_master===true` before accepting the first
exchange; the first JWT is discarded and a second call to `argus_exchange_admin_code` is
made. However, the field-app makes only the single `argus_exchange_code` call and
accepts any returned JWT.

**Fix:** Add a rejection guard for `is_admin` codes in `argus_exchange_code`. This
requires a new migration (e.g., `0014_...`) since 0013 is already applied live:

```sql
-- In argus_exchange_code, after the observer check (currently line ~128 of 0009):
if coalesce(v_token.is_admin, false) then
  return jsonb_build_object('error', 'Admin-Code — nur für die Leitungs-Oberfläche gültig');
end if;
```

The field-app's `exchangeCode()` function already surfaces the server error string to
the user, so no client-side change is needed.

## Warnings

### WR-01: Unescaped Photo Data in `innerHTML` `src` Attribute

**File:** `docs/leitung-*.html:1650`

**Issue:** The photo value returned by `argus_governance_photo` is placed directly into
an `innerHTML` string as a `src` attribute value without escaping or validation:

```js
ov.innerHTML='<img src="'+photo+'" alt="Patientenfoto" ...>'
```

`photo` is a TEXT field from `public.patients.photo`, written by field devices. While
`argus_governance_photo` is master-only (no Admin can call it), a compromised or
malicious field device could store a payload such as `" onerror="...` in the photo
column. Modern browsers block `javascript:` in `img src`, but an inline event handler
injected via attribute breakout would execute in the Leitungs-Seite's origin context,
where a MasterToken is held in `sessionStorage`. The Supabase anon-key is also in the
page. This is a stored-XSS vector originating from field-device data.

**Fix:** Either use `document.createElement`/`setAttribute` (which never executes
scripts regardless of content), or validate that `photo` begins with `data:image/` before
using it:

```js
// Safe variant
var img = document.createElement('img');
img.alt = 'Patientenfoto';
img.style.cssText = 'max-width:100%;max-height:78%;object-fit:contain;border-radius:8px';
if(photo && photo.startsWith('data:image/')) {
  img.src = photo;
} else {
  img.alt = 'Foto nicht darstellbar';
}
ov.appendChild(img);
// then append the text div separately
```

### WR-02: `Math.random()` Used for Short-Code Generation in Master Insert Path — Weak Entropy

**File:** `docs/leitung-*.html:832-835`

**Issue:** `genShortCode()` uses `Math.random()` (not cryptographically secure) to
generate short codes for new tokens inserted via the Master path:

```js
function genShortCode(){
  var AL="ABCDEFGHJKLMNPQRSTUVWXYZ23456789";
  function blk(){var s='';for(var i=0;i<4;i++)s+=AL[Math.floor(Math.random()*AL.length)];return s;}
  return blk()+'-'+blk();
}
```

This function is used in `makeGast`, `makeObserver`, `makeAdmin`, and `makeLink` when
inserting new tokens directly from the Leitungs-Seite. `Math.random()` is a PRNG seeded
by the engine; its output is statistically predictable given knowledge of the engine
state. Short codes are 8 characters from a 32-symbol alphabet (32^8 = ~1 trillion
combinations), which is a large space, but weakened PRNG reduces effective entropy.
The server-side `argus_admin_issue_gast` correctly uses `gen_random_bytes` for its
short codes; the client-side path does not match this security level.

**Fix:** Replace `Math.random()` with `crypto.getRandomValues()`, which is available in
all modern browsers and the Leitungs-Seite already uses it for `genToken()`:

```js
function genShortCode(){
  var AL="ABCDEFGHJKLMNPQRSTUVWXYZ23456789";
  var buf=new Uint8Array(8);
  crypto.getRandomValues(buf);
  function blk(b){ return AL[b % AL.length]; }  // 256%32=0, no modulo bias
  return [0,1,2,3].map(function(i){return blk(buf[i]);}).join('')
       + '-'
       + [4,5,6,7].map(function(i){return blk(buf[i]);}).join('');
}
```

### WR-03: `argus_lage()` Admin Branch Exposes `verbund_gruppe` (Raw `merge_group_id` UUID)

**File:** `supabase/migrations/0013_phase414_admin_rolle.sql:365-366`

**Issue:** The `argus_lage()` function (fully reproduced in 0013) includes
`verbund_gruppe: c.merge_group_id` in the CCP-level JSON returned to Admin callers.
`merge_group_id` is an internal UUID linking CCPs that have been merged into a combined
command. Its disclosure to an Admin-role caller is a minor scope leak: the Admin role is
described as seeing only "anonymous own-Präsidium counts" with "no patient rows, no
names/photos/vitals," yet this UUID could potentially be correlated with data from other
RPCs or used to infer operational structure. The `verbund` boolean (`c.merge_group_id is
not null`) already conveys the same semantic information without the raw UUID.

**Fix:** Remove `verbund_gruppe` from the Admin branch, or conditionally exclude it.
Since `create or replace function` replaces the single `argus_lage` function shared by
both Observer and Admin paths, the simplest fix is to always strip the UUID from the
response when the caller is an Admin:

```sql
-- Replace verbund_gruppe line with:
'verbund_gruppe', case when public.argus_is_admin() then null
                       else c.merge_group_id end,
```

Alternatively, accept the disclosure given that the UUID itself is not patient data and
the operational correlation risk is minimal — but document the decision.

### IN-01: Smoke-Test in SELF-HOSTING.md Does Not Include Admin-Code Negative Test

**File:** `docs/SELF-HOSTING.md:316-362`

**Issue:** Section 10 (Smoke-Test-Drehbuch) covers the normal device-code and Master
flows but adds no smoke-test step for the Admin role introduced by migration 0013. Given
that the Admin privilege-escalation boundary is the primary security requirement of this
phase, an operator self-hosting the system has no prescribed test to verify that:

- An Admin code cannot be exchanged via `argus_exchange_code` (field-app path) for a
  device JWT with `praesidium_id` (directly relevant to CR-02 above).
- An Admin JWT cannot read `/rest/v1/patients` or access governance RPCs.

**Fix:** Add a step 9 to section 10 covering Admin-code negative tests. A minimal
addition:

```
9. **Admin-Code-Tests (Pflicht nach Migration 0013):**
   a. Admin-Code über `rpc/argus_exchange_admin_code` einlösen → JWT dekodieren:
      `is_admin=true`, `admin_praesidium_id` gesetzt, KEIN `is_master`, KEIN
      `praesidium_id`. 
   b. Admin-Code gegen `rpc/argus_exchange_code` (Feld-App-Pfad) einlösen →
      Erwartung: `{"error":"Admin-Code — ..."}` (erfordert Fix aus CR-02).
   c. Mit Admin-JWT: `GET /rest/v1/patients?select=id` → `[]`.
   d. Mit Admin-JWT: `rpc/argus_admin_issue_gast` mit FREMDER `p_praesidium_id`
      → Exception.
```

### IN-02: `doLogin` Double-Exchange Produces Admin-JWT Even If Admin Code Was Also Accepted by `argus_exchange_code` — Misleading Log

**File:** `docs/leitung-*.html:641-689`

**Issue:** The dual-exchange login flow in the Leitungs-Seite (comment on line 628 reads
"Doppel-Log vermeiden") correctly calls `argus_exchange_admin_code` only when the master
attempt does not yield a master JWT. However, because `argus_exchange_code` (pre-fix of
CR-02) accepts admin codes and returns a JWT silently, the governance_log will NOT record
an `admin_login` entry for that first call (only `gast_join` would be logged for gast
codes; non-gast non-master non-observer codes create no log entry). After CR-02 is fixed
the first call will return an error, and the second call will log `admin_login` normally.
Until CR-02 is fixed, an admin user who enters their code in the Leitungs-Seite is
silently getting a device JWT discarded, a second call logs the admin login — net result
is correct for the Leitungs-Seite, but the discarded device JWT was briefly valid. This
is a documentation/logging gap rather than a blocking defect.

**Fix:** Tracked through fixing CR-02 (which makes the first call return an error, so
no transient device JWT is ever created).
