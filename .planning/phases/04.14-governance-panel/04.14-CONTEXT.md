<decisions>
## Implementation Decisions (locked)

### Rolle „Präsidiums-Admin" (NEU)
- Token-Art **`is_admin`** (boolean, Muster wie `is_master`/`is_observer`/`gast`)
  + Claim **`admin_praesidium_id`** + Helper `argus_admin_praesidium_id()`
  (analog `argus_observer_praesidium_id()`, Migration 0005). **NIE `is_master`** im JWT.
- Capabilities — **NUR fürs eigene Präsidium:**
  - **24h-Gast-Code ausgeben + sperren** (KEINE Einmal-/Dauerhaft-Codes).
  - **eigene anonyme Lage** sehen (wie Beobachter, auf `admin_praesidium_id` begrenzt).
  - KEINE Einsatzprotokolle, KEIN Foto-Abruf, KEINE Präsidiums-Anlage, KEINE Fremd-Präsidien.
- **MasterUser gibt Admin-Token aus** (über die Leitungs-Seite, je Präsidium).
- `jti`-Sofortsperre (`argus_token_active`, Migration 0007) gilt automatisch.

### Admin-Surface = rollen-adaptive Leitungs-Seite (Weg B)
- KEINE neue Seite je Rolle. Die **bestehende Leitungs-Seite** wird **rollen-bewusst**:
  Master → volle Governance; Präsidiums-Admin → reduzierte Ansicht (eigenes Präsidium:
  Gast-Code + eigene Lage). Fundament für künftige Rollen. RLS bleibt die echte Grenze.

### Weitere In-Scope-Bausteine
- **QR-Ausgabe für Gast-Codes:** selbst-enthaltener Inline-QR-Generator (KEIN externes CDN),
  Deep-Link, der die Feld-App/Installseite mit vorausgefülltem Code öffnet.
- **Übungspräsidium „leeren":** Master-Aktion (Demo-CCPs/Patienten/Checklisten des
  Schulungs-Präsidiums entfernen) + Demo-Befüllung **opt-in** statt automatisch.
- **Audit-/Protokoll-Ansicht** im Panel ausbauen (kürzelbasiert; personenscharf erst mit Stufe 1).

### Sicherheits-Leitplanken (nicht verhandelbar)
- **Privilege-Escalation-Schutz:** Admin erzeugt/sperrt NIE master/admin/observer-Tokens;
  Code-Ausgabe/-Sperre als `security definer`-RPCs mit harter Prüfung
  `Ziel-Präsidium == argus_admin_praesidium_id()` UND Token-Art nicht privilegiert.
- **REST-Negativtests Pflicht** (Muster Observer 4.12): Admin-JWT → Fremd-Präsidium /
  Protokolle / Fotos / Token-Eskalation = jeweils verweigert.
</decisions>
