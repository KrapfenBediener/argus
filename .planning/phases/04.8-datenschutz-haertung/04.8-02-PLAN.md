# Plan 04.8-02: Datenbank-Fundament — Einsatz-Lebenszyklus, Purge, Governance (T2/T1 serverseitig)

**Phase:** 4.8 — Datenschutz-Härtung
**Wave:** 1 (unabhängig von 04.8-01; Voraussetzung für 04.8-03/04/05)

## Objective

Eine versionierte Migration `0002_phase48_datenschutz.sql` liefert den gesamten
serverseitigen Unterbau für T2 (Einsatz abschließen + automatische Löschung)
und T1 (Foto-Schalter, Foto-Fristen, Governance-Protokoll):
Spalten, Protokoll-Tabellen, RPCs nach dem pgjwt-/SECURITY-DEFINER-Muster aus
`0001_phase4_jwt_rls.sql`, RLS-Härtung und ein zeitgesteuerter Purge-Job.
Angewendet wird über die Supabase Management API (curl + ephemerer PAT) auf
Projekt `sehuosjyjmrpzcqrelej` — kein CLI, kein node, keine Edge Function.

**Rollen-Abbildung (begründete Entscheidung, CONTEXT „Claude's Discretion"):**
Die „MasterUser-/Governance-Rolle" wird auf den bestehenden `is_master`-JWT-Claim
abgebildet (MasterToken). Der MasterMedic hat einen normalen Präsidiums-Token —
genau wie gefordert ist Governance damit von der MasterMedic-Rolle getrennt.
Eine neue Claim-Form ist nicht nötig; `argus_is_master()` existiert bereits und
ist RLS-erprobt.

**Foto-Lebenszyklus-Abgleich T1/T2:** T2 nennt „Fotos sofort löschen" beim
Abschluss, T1 präzisiert den Foto-Lebenszyklus (72 h Governance-Fenster nach
Abschluss, verlängerbar, dann endgültige Löschung). Umsetzung folgt T1 als der
präzisierten Entscheidung: beim Abschluss verschwinden Fotos sofort von den
Geräten und aus der Normalansicht (Plan 04.8-03/04), in der Cloud bleiben sie
bis `photo_purge_after` (Abschluss + 72 h, nur via Governance verlängerbar) und
werden dann endgültig gelöscht. Eine Sofort-Cloud-Löschung würde die
T1-Fristverlängerung unmöglich machen.

**Annahme pg_cron:** pg_cron ist auf dem Supabase Free Tier verfügbar. Absicherung
doppelt: (a) die Migration legt den Cron-Job in einem fehlertoleranten Block an,
(b) die App ruft `argus_run_purge()` zusätzlich opportunistisch beim Start auf
(Plan 04.8-03) — damit läuft der Purge auch, wenn das Free-Tier-Projekt pausiert
war und erst durch App-Traffic aufwacht.

## Context

- `supabase/migrations/0000_base_schema.sql` — Tabellen `ccps` (hat bereits `closed_at bigint`), `patients` (Spalte `photo text`), `checklists`, Grants, RLS
- `supabase/migrations/0001_phase4_jwt_rls.sql` — Muster: SECURITY DEFINER RPC, `argus_praesidium_id()`, `argus_is_master()`, Policy-Stil; `argus_ccps_rw` (Z. 134–136) erlaubt bisher jedem Präsidiums-Gerät beliebige ccps-Updates
- Zeitstempel-Konvention: bigint in JS-Millisekunden (`nowMs()`/`Date.now()`), NICHT timestamptz (vgl. used_at-Bugfix in 0001)
- `ccps.updated_at` wird von der App nicht gepflegt — Inaktivität muss über `max(patients.updated)` + `ccps.created_at` bestimmt werden

<action>
`supabase/migrations/0002_phase48_datenschutz.sql` anlegen (idempotent: if not
exists / or replace / drop policy if exists, Stil wie 0001). Inhalt:

1. **Spalten auf `public.ccps`:** `einsatz_typ text` (null = offen; beim Abschluss
   'uebung' oder 'einsatz'), `purge_after bigint` (ms-Zeitpunkt der Datenlöschung),
   `photo_purge_after bigint` (ms-Zeitpunkt der endgültigen Foto-Löschung),
   `photos_allowed boolean not null default false` (T1-Schalter, Default AUS).

2. **Tabelle `public.purge_log`** (inhaltsfrei): id uuid pk default, at timestamptz
   default now(), ccp_id uuid, kennung text, reason text ('frist' | 'inaktiv' |
   'foto_72h'), patient_count int, photo_count int, checklist_count int.
   Grant select to anon; RLS aktiv; Policy `argus_purge_log_select` for select
   using `argus_is_master()`; KEINE Insert-Policy für anon (es schreiben nur
   SECURITY-DEFINER-Funktionen).

3. **Tabelle `public.governance_log`:** id uuid pk default, at bigint (ms),
   ccp_id uuid, patient_id text, kuerzel text, action text ('foto_view' |
   'frist_verlaengert'), begruendung text, neue_frist bigint. Grant select to
   anon; RLS aktiv; Policy `argus_governance_log_select` for select using
   `argus_is_master()`; keine anon-Schreib-Policy.

4. **RPC `argus_close_einsatz(p_ccp_id uuid, p_typ text, p_frist_tage int)`**
   security definer, grant execute to anon: Berechtigung = `argus_is_master()`
   ODER der CCP gehört zum `argus_praesidium_id()` des Aufrufers (sonst
   Fehler-jsonb; die MasterMedic-Eigenschaft ist nur App-seitig bekannt —
   serverseitig ist das Präsidium die Grenze, als Kommentar dokumentieren).
   p_typ muss 'uebung' oder 'einsatz' sein, p_frist_tage zwischen 1 und 365.
   Wirkung — bei gesetzter `merge_group_id` für ALLE CCPs der Gruppe (Einsatz =
   Verbund), sonst nur für den einen CCP: `closed_at` = jetzt-ms (falls null),
   `einsatz_typ` = p_typ, `purge_after` = closed_at + p_frist_tage Tage in ms,
   `photo_purge_after` = closed_at + 72 h in ms, `join_token` = null
   (Einsatz-Beitritt gesperrt). Rückgabe-jsonb mit closed_at, purge_after,
   photo_purge_after, betroffener CCP-Anzahl.

5. **RPC `argus_run_purge()`** security definer, grant execute to anon (löscht
   nur Fälliges, gibt nur Zähler zurück — gefahrlos öffentlich aufrufbar).
   Drei Schritte, jeweils mit `purge_log`-Eintrag pro betroffenem CCP:
   (a) Foto-Purge: für CCPs mit `photo_purge_after` <= jetzt UND
   `exists (select 1 from patients where ccp_id = ccps.id and photo is not null)`
   — die exists-Bedingung ist Pflicht als Wiederholungs-Guard: `photo_purge_after
   <= now` bleibt nach dem ersten Lauf dauerhaft wahr, ohne Guard würde der
   stündliche Cron denselben CCP jede Stunde erneut matchen und `purge_log`
   mit leeren foto_72h-Einträgen fluten. Wirkung: alle `patients.photo` der
   CCP-Patienten auf null setzen (photo_count = Anzahl genullter Fotos;
   reason 'foto_72h').
   (b) Daten-Purge: für CCPs mit `purge_after` <= jetzt: patient-/checklist-Rows
   zählen, dann `delete from patients where ccp_id=...`, `delete from checklists
   where ccp_id=...`; die ccps-Row bleibt als inhaltsleerer Tombstone (ort='',
   master_medic='', join_token=null) — Geräte erkennen daran den Abschluss für
   die lokale Bereinigung; reason 'frist'.
   (c) Auffangnetz: offene CCPs (closed_at null), deren letzte Aktivität
   (greatest aus created_at als ms, coalesce(max(patients.updated),0)) länger
   als 60 Tage zurückliegt: wie (b) inkl. Foto-Nullung, zusätzlich closed_at =
   jetzt setzen; reason 'inaktiv'. Rückgabe-jsonb mit Zählern je Schritt.
   Auch (b) und (c) brauchen einen Wiederholungs-Guard: nur CCPs matchen, die
   noch zu purgende Daten haben (vorhandene patients-/checklists-Rows) bzw.
   deren Tombstone-Zustand noch nicht hergestellt ist — kein Log-Eintrag bei
   No-op-Läufen.

6. **RPC `argus_governance_list()`** security definer, grant execute to anon:
   wirft Fehler wenn nicht `argus_is_master()`. Liefert OHNE Foto-Daten und
   OHNE Log-Eintrag die Übersicht: pro Patient mit `photo is not null` und
   (status='gpa' ODER zugehöriger CCP closed_at not null): patient_id, num,
   ccp-Kennung, status, ccp_id, photo_purge_after des CCP.

7. **RPC `argus_governance_photo(p_patient_id text, p_kuerzel text)`** security
   definer, grant execute to anon: wirft Fehler wenn nicht `argus_is_master()`
   oder wenn p_kuerzel leer. Gibt das `photo`-Feld des Patienten zurück und
   schreibt VOR der Rückgabe einen `governance_log`-Eintrag (action 'foto_view',
   kuerzel, patient_id, ccp_id, at = jetzt-ms). Jeder Foto-Abruf = ein Eintrag.

8. **RPC `argus_extend_photo_frist(p_ccp_id uuid, p_kuerzel text, p_grund text,
   p_stunden int default 72)`** security definer, grant execute to anon: wirft
   Fehler wenn nicht `argus_is_master()`, wenn p_grund leer/nur Whitespace oder
   p_stunden nicht in 1..720. Setzt `photo_purge_after` = greatest(jetzt,
   bisheriger Wert) + p_stunden in ms; schreibt governance_log (action
   'frist_verlaengert', begruendung = p_grund, neue_frist = neuer Wert,
   kuerzel, ccp_id). Rückgabe: neue Frist als jsonb.

9. **RLS-Härtung patients:** `argus_patients_rw` (for all) ersetzen durch
   `argus_patients_select` (for select; Bedingung wie bisher: Master oder
   Präsidiums-CCP) und `argus_patients_write` (for insert, update, delete;
   zusätzlich: der zugehörige CCP hat `closed_at is null` — für Nicht-Master
   ist ein abgeschlossener Einsatz schreibgesperrt; Master bleibt
   uneingeschränkt). Kommentar: verspätete Offline-Flushes auf abgeschlossene
   Einsätze schlagen damit bewusst fehl; die Geräte bereinigen lokal
   (Plan 04.8-03).

10. **RLS-Härtung ccps (Sperre nicht umkehrbar machen):** `argus_ccps_rw`
    (for all, aus 0001 Z. 134–136) ersetzen durch `argus_ccps_select`
    (for select; Bedingung wie bisher: `argus_is_master()` oder
    `praesidium_id = argus_praesidium_id()`) und `argus_ccps_write`
    (for insert, update, delete; USING für Nicht-Master zusätzlich an
    `closed_at is null` gebunden: ein abgeschlossener CCP ist für
    Präsidiums-Geräte komplett update-/delete-gesperrt — damit kann kein
    Client per direkter REST-API `closed_at = null` setzen, `join_token`
    wiederherstellen oder `purge_after`/`photo_purge_after` manipulieren;
    Master bleibt uneingeschränkt). WICHTIG zur Richtung der Bedingung:
    die `closed_at is null`-Prüfung gehört in die USING-Klausel (Zustand der
    BESTEHENDEN Row), NICHT in WITH CHECK — so bleibt das Setzen von
    `closed_at` auf einer offenen Row erlaubt (bestehender Pfad
    „CCP/Verbund löschen" in index.html setzt closed_at direkt), nur das
    nachträgliche Ändern einer geschlossenen Row ist blockiert. Die
    SECURITY-DEFINER-RPCs (insb. `argus_close_einsatz`,
    `argus_extend_photo_frist`) sind von RLS nicht betroffen. Konsistent mit
    der Zero-Trust-Linie aus Phase 4 — als Kommentar in der Migration
    dokumentieren.

11. **pg_cron:** `create extension if not exists pg_cron;` und — in einem
    DO-Block mit exception-Handler, damit die Migration auf Instanzen ohne
    pg_cron nicht bricht — `cron.schedule('argus_purge', '17 * * * *',
    'select public.argus_run_purge()')` (stündlich; vorher per
    `cron.unschedule` idempotent machen, Fehler ignorieren). Im Kommentar:
    Fallback ist der opportunistische App-Start-Aufruf (Plan 04.8-03).
