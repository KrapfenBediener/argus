<decisions>
## Implementation Decisions (locked)

### 1. Zentrale Konfiguration
- Supabase-URL + Anon-Key aus dem Code in EINE zentrale, build-freie
  Konfigurationsdatei (z. B. `config.js` im Projektroot) — Konsumenten:
  `index.html` (Feld-App) UND die Leitungs-Seite (`docs/leitung-*.html`,
  Dateiname via untracked LEITUNG-URL.md — D-06 gilt weiter: nie in
  committete Texte).
- Die Datei enthält NUR den öffentlichen Anon-Key + URL (beides steht heute
  schon public in index.html — kein neues Geheimnis, KEINE Service-Keys).
- PWA-/Offline-Verhalten unverändert: config.js in den SW-Precache; Reihenfolge
  beachten (config vor Hauptscript); App muss bei fehlender/kaputter Config
  einen klaren Fehlerhinweis zeigen statt still zu brechen.
- Trainings-Sandbox und alle bestehenden Flows unangetastet (Speicher-Naht
  aus CLAUDE.md nicht verändern).

### 2. docs/SELF-HOSTING.md (öffentlich committbar)
- Zielgruppe: fachkundige Person OHNE Projektkenntnis (BITBW-Admin).
- Inhalt: (a) Varianten Supabase self-hosted (Docker Compose) vs. verwaltetes
  Postgres + PostgREST-kompatible Schicht — ehrlich dokumentieren, was geht;
  (b) Migrationen 0000–0004 in Reihenfolge anwenden (Ein-Schritt-Apply);
  (c) Server-Abhängigkeiten einrichten: pgjwt, Vault (JWT-Secret des
  Code-Exchange-RPC!), pg_cron (Purge-Job), Realtime — je: wofür, wie prüfen;
  (d) frische Zugangs-Codes/MasterToken erzeugen (wie, ohne alte zu
  übernehmen); (e) config.js auf die neue Instanz zeigen lassen;
  (f) Smoke-Test-Drehbuch (Code einlösen → CCP anlegen → Patient → Abschluss →
  Leitungs-Seite → Purge-Lauf prüfen).
- KEINE Secrets, keine internen Begriffe/Strategie, kein Leitungs-Dateiname
  (Muster-Schreibweise) — Datei ist public.
- **Betriebsvorgaben für Lizenznehmer** als eigener Abschnitt: nur verwaltete
  Dienstgeräte (MDM, Gerätesperrcode), Kürzel-Liste je Einsatz beim
  Einsatzleiter (Zuordnung Kürzel → Person), Einsatz-Codes nur mündlich/Funk.
- Zielbild M1 + Rolle der Eigentümer-Instanz (Dev/Schulung, Fiktivdaten)
  kurz dokumentieren; Verweis auf Lizenz-Rahmen OHNE Vertragsdetails.

### 3. Kompatibilitäts-Audit (Teil der Phase, ehrlich dokumentieren)
- Migrationen 0000–0004 + RPCs daraufhin prüfen, was Supabase-spezifisch ist
  (vault.*, cron.*, realtime-Publikationen, auth-Schema-Annahmen) und je
  Abhängigkeit festhalten: Pflicht / optional / Ersatzweg in self-hosted.
- Befunde, die sich NICHT rein dokumentarisch lösen lassen (z. B. Vault in
  self-hosted), als klare Voraussetzungen in SELF-HOSTING.md — KEINE
  spekulativen Code-Umbauten in dieser Phase.

### 4. Release
- index.html/sw.js ändern sich (config-Auslagerung, Precache) → Release gem.
  Konvention (v0.24.0 vorgeschlagen, SW-Cache +1, CHANGELOG; WHATS_NEW knapp —
  für Nutzer unsichtbare Änderung, kein UPDATE-Sheet).
- Drehbuch-DAUERREGEL: keine UI-Änderung erwartet → Prüfung dokumentieren.

### Claude's Discretion
- Name/Format der Config (config.js global vs. JSON+fetch) — Constraint:
  build-frei, offline-tauglich, vor Hauptscript verfügbar, EIN Ort für beide
  Seiten (Feld-App + Leitungs-Seite; relativer Pfad docs/ beachten).
- Struktur von SELF-HOSTING.md.
- Ob PROD-SETUP.md (intern) auf SELF-HOSTING.md verweist/abgelöst wird.

</decisions>
