## Summary

Phase 5.1 delivers Person-Login auto-detection, Echt/Schulung-picker with twin re-exchange, server-side AFTER-triggers for D-06 audit, and the 'normal' role unlock. The security-critical path (server-side twin resolution, argus_is_master guard, append-only audit, CR-02 intact) is structurally sound. Two correctness blockers were found: a Person-session bypass of the init access-gate that lets a valid-JWT, Person-session user skip straight to CCP operations without `_praesidiumId` being in the unlocked list; and an unvalidated p_scope parameter in the RPC that silently treats any non-'schulung' string as 'echt' rather than rejecting it. Three warnings relate to a missing client-side praesidium guard for role-change-to-normal, a tqLabel XSS-adjacent pattern via `innerHTML`, and an offline mode-switch that discards picker-mode state incoherently. Two info items cover minor quality gaps.

## Critical Issues

### CR-01: Person-Session Bypasses the `hasAccess` / `isUnlocked` Gate in `init()`

**File:** `index.html:3789-3792`

**Issue:** The init access gate is:

```js
var hasAccess = _isMaster || (!!localStorage.getItem('argus_jwt') && getUnlocked().length>0);
if(!hasAccess || !_praesidiumId || !isUnlocked(_praesidiumId)){
  state.view='praesidium'; render(); return;
}
```

A Person-session user (role='normal', `argus_role` in localStorage, JWT present) enters `doUnlock` → `exchangePersonCode` → calls `addUnlock(pv.praesidium_id, null)` at line 831 and sets `_praesidiumId` at line 832. So far so good for the normal first-login flow.

But on a **subsequent cold start** (app closed and reopened), `init()` restores `_praesidiumId` from `localStorage.getItem('argus_praesidium_id')` (line 3700) and `_usbnk`/`_argusRole` from `argus_usbnk`/`argus_role` (lines 3705-3706). However, the `hasAccess` check requires `getUnlocked().length>0`. `addUnlock` stores entries in `argus_unlocked` with `exp=0` (permanent), so that part is fine.

The actual gap is narrower but real: **when the Schulungs Re-Exchange succeeds** (picker switches to 'schulung'), `_praesidiumId` is updated to the twin's ID at lines 3124-3128, and `argus_praesidium_id` in localStorage is overwritten with the twin praesidium UUID. But `addUnlock` is never called for the twin's praesidium UUID — only the original Echt-praesidium was added to `argus_unlocked`. On the next cold start, `_praesidiumId` = twin UUID, `isUnlocked(twin UUID)` = false (because only the original UUID is in argus_unlocked), causing the check at line 3790 to route to `state.view='praesidium'` instead of resuming the session. The user must re-authenticate from scratch.

More critically: if an attacker can tamper `argus_praesidium_id` in localStorage to match a praesidium UUID that _is_ unlocked (e.g., the original echt UUID), while also having a schulung-scope JWT, the `isUnlocked` check passes with the echt UUID while `_praesidiumId` points to the echt UUID — but the JWT contains the twin's `praesidium_id`. The RLS will correctly enforce the JWT claim, so no data-access escalation occurs on the server. The client-side mismatch does, however, mean `_praesidiumSchulung` will reflect the echt präsidium's `schulung` flag (false) rather than the twin's (true), causing the **Schulungsumgebung banner to disappear** in `vHome()` — a data-mixing confusion risk on re-login after a schulung session. This is an Echt/Schulung mixing path (D5.1-03, T-053-02 concern).

**Fix:** After a successful Schulungs Re-Exchange at the pickertab handler (line 3124), also add the twin praesidium to the unlocked list so subsequent cold starts find it:

```js
// After: _praesidiumId = reex.praesidium_id||null;
if(_praesidiumId){
  addUnlock(_praesidiumId, null);  // twin scope also permanently unlocked
  localStorage.setItem('argus_praesidium_id', _praesidiumId);
  localStorage.setItem('argus_praesidium_name', _praesidiumName);
}
```

### CR-02: `p_scope` Not Validated in `argus_exchange_person_code` — Arbitrary String Silently Treated as 'echt'

**File:** `supabase/migrations/0019_phase51_twin_scope.sql:84,135`

**Issue:** The function signature accepts `p_scope text default 'echt'` with no whitelist check. The twin-resolution branch fires only on `p_scope = 'schulung'` (line 135). Any other value — e.g. `p_scope='admin'`, `p_scope='; drop table access_tokens; --'`, or an accidental typo — silently falls through and is treated identically to `'echt'`, issuing a JWT with `praesidium_id = v_token.praesidium_id` and logging `scope = coalesce(p_scope, 'echt')` in the return payload (line 207).

The audit log line 190-192 logs `praesidium_id = v_eff_praesidium` but does not log `p_scope`. The return value at line 207 echoes back whatever the client sent as `scope`. A client that passes `scope='schulung-admin'` gets back `scope='schulung-admin'` in the response — the client's `exchangePersonCode` stores `data.scope||effectiveScope` (index.html line 687). Since `effectiveScope` in the client is already sanitized to `'echt'`/`'schulung'` (line 656), the client-side defense holds. But the RPC itself provides no server-side rejection; a direct API call with an arbitrary `p_scope` is silently accepted. This is a defence-in-depth failure for an append-only authenticated surface — the scope field in the response is untrustworthy if called directly.

**Fix:** Add a whitelist guard early in the function body, after the code normalization block:

```sql
-- Scope-Validierung: nur 'echt' und 'schulung' sind erlaubt.
if p_scope not in ('echt', 'schulung') then
  return jsonb_build_object('error', 'Ungültiger Scope — erlaubt: echt, schulung');
end if;
```

## Warnings

### WR-01: Role-Change to 'normal' in Leitung Does Not Client-Side Guard Against Missing Praesidium

**File:** `docs/leitung-*.html:1901-1925`

**Issue:** `doPersonRole(sc, usbnk, oldRole, oldPid)` calls `argus_master_role_change_person` with the new role but does not send a praesidium update. The RPC (0018, line 227-229) correctly blocks role='admin' without praesidium but does **not** block role='normal' without praesidium — and it cannot, because the RPC only updates the `role` field without touching `praesidium_id`. If a Master changes a flz/master token (which has `praesidium_id=null`) to 'normal', the resulting 'normal' token will have `praesidium_id=null`. When this token is exchanged, `argus_exchange_person_code` issues a JWT with `praesidium_id=null` (line 175-177 of 0019 — `case when v_token.role in ('master','flz') then null else v_eff_praesidium end`, but at this point `role='normal'` so it would use `v_eff_praesidium` which was set from `v_token.praesidium_id = null`). The Feld-App's `doUnlock` (index.html line 826-827) then rejects this with "Person-Code ohne Präsidium" — a confusing user experience that leaves the field operator unable to log in.

The server-side RPC should enforce the same praesidium constraint for 'normal' that it already enforces for 'admin' (the constraint is present in `argus_master_issue_person` for both roles but missing from `argus_master_role_change_person`).

**Fix (0018 or a 0020 patch migration):** In `argus_master_role_change_person`, add after the whitelist check:

```sql
-- 'normal' (wie 'admin') erfordert Präsidiumszuordnung (Konsistenz mit issue).
if p_new_role = 'normal' and v_t.praesidium_id is null then
  raise exception 'Normal-Rolle erfordert Präsidium — bitte erst Token neu ausgeben';
end if;
```

And in `doPersonRole` in leitung, warn the operator when changing to 'normal' with a null praesidium.

### WR-02: `tqLabel` Result Assigned via `innerHTML` with `_tl.textContent` Sanitization — Logic Error Risk

**File:** `index.html:3628`

**Issue:** The TQ button text is updated in the 1-second setInterval via:

```js
var _tl=document.createElement('span');
_tl.innerHTML=tqLabel(state.edit);
tb.textContent=_tl.textContent;
```

`tqLabel` calls `esc(p.tqSite)` internally (line 1173) — the HTML escaping is correct and the outer `textContent` assignment makes the final DOM write safe. However, the intermediate `_tl.innerHTML = tqLabel(...)` step still parses the escaped HTML entities as DOM text, then `.textContent` extracts the decoded text and assigns it. This means `&amp;`, `&lt;` etc. are decoded twice: once by `esc()` on the way in, and once by the HTML parser on the `.innerHTML` assignment. A `tqSite` value of `<script>` would be stored as `&lt;script&gt;` by `esc()`, placed into innerHTML making the DOM show `<script>` as literal text, then `.textContent` would extract `<script>` (decoded) and set `tb.textContent` to the string `<script>` — which is still safe (textContent assignment never executes scripts). But the double-decode means a `tqSite` of `&amp;` displays as `&` rather than `&amp;`, causing cosmetically incorrect output.

More importantly, the `_tl.innerHTML=...` line is architecturally unnecessary — `tqLabel` returns a safe string and `tb.textContent` could be set directly. The `innerHTML` step is dead-code with an unintended double-decode side effect.

**Fix:** Remove the intermediate element and assign directly:

```js
tb.textContent = tqLabel(state.edit);
```

And adjust `tqLabel` to not use `esc()` internally (since the consumer is textContent, not innerHTML):

```js
function tqLabel(p){
  var ms=nowMs()-p.tqStart;
  var unit=ms>=3600000?' Std':' min';
  return 'TQ'+(p.tqSite?' ('+p.tqSite+')':'')+' läuft seit '+fmtDur(ms)+unit+' — tippen zum Stoppen';
}
```

### WR-03: Offline Tab-Switch Leaves Picker-Mode State Incoherent

**File:** `index.html:3111-3134`

**Issue:** The `pickertab` handler for a Person-session performs the mode check, shows the `confirmModal` (which the user confirms), then checks `navigator.onLine`. If offline, it shows a toast and `return`s — so far correct. However, `setPickerMode(newTab)` at line 3133 is called unconditionally after the `if(isPersonSess)` block. If `isPersonSess` is true but the code inside it returned early due to offline (`return` at line 3113), execution does NOT reach `setPickerMode` (because the early return exits the handler). So the picker state is not updated — that part is correct.

The problem is the **non-Person session path**: `if(!isPersonSess)`, there is no offline guard before `setPickerMode(newTab)`. For a Sammelcode session, the tab switch just persists the new tab and re-renders (lines 3133-3134). Since Sammelcode sessions use the schulung flag of the praesidium directly (no re-exchange needed), this is acceptable. But the `confirmModal` at line 3096 fires for all tab switches — including Sammelcode sessions where a re-exchange is not needed and offline is not a concern. This wastes a confirmation step for an offline Sammelcode user switching tabs, and the confirmation text says "Im Schulungsmodus werden NUR Übungsdaten erfasst — niemals echte Patientendaten" even when the user is about to switch to an empty list (no schulungs-praesidium in scope). This is a false-confirmation UX issue that can confuse operators under stress.

Additionally: after a successful Person-session re-exchange in the pickertab handler, if `reex.praesidium_id` is null (which cannot happen for 'normal' but could for 'admin' in edge cases), `_praesidiumId` is set to null and `argus_praesidium_id` in localStorage is NOT updated (the update is conditional on `if(_praesidiumId)` at line 3126), leaving a stale value in localStorage. On the next cold start, the stale praesidium_id would be loaded and the session would appear to be in the previous praesidium.

**Fix:** Add `else{ setPickerMode(oldTab); toast("..."); return; }` after the offline return in the Person-session block instead of falling through to the unconditional `setPickerMode`. Also add a null guard: if `reex.praesidium_id` is null after re-exchange, do not proceed with the tab switch and show an error.

### IN-01: `argus_picker_mode` Not Cleared by `applyRevokedLock`

**File:** `index.html:743-766`

**Issue:** `applyRevokedLock()` removes the Person-session localStorage keys (lines 747-760) including `argus_usbnk`, `argus_role`, and `argus_person_praesidium`. It does not remove `argus_picker_mode`. After a revocation and re-login with a different account (or a new Sammelcode), the picker starts in whatever tab the revoked Person-session had last used (potentially 'schulung'). For a new Sammelcode user whose praesidium has no schulungs-zwilling, this shows an empty Schulung tab on first login — confusing for field use.

**Fix:** Add `localStorage.removeItem('argus_picker_mode');` inside the `applyRevokedLock` try block alongside the other removals.

### IN-02: `argus_audit_patients` Trigger Does Not Log `patient_photo` When Photo Is Updated (Not Added)

**File:** `supabase/migrations/0018_phase51_feld_audit_normal.sql:66`

**Issue:** The photo-logging condition is:

```sql
if NEW.photo is not null and OLD.photo is null then
  v_action := 'patient_photo';
```

This fires only when a photo is first added (null → non-null). If a photo is replaced (non-null → different non-null value), or if a photo is deleted (non-null → null, which should not happen by design but could via a bug), no audit entry is created. The D-06 catalog defines `patient_photo` as the action for photo activity. A photo-replacement (e.g., operator re-takes photo) silently falls through to the `else` branch and generates no log entry.

Per DSB-Freigabe (memory: fotos dürfen dauerhaft aktiv), photos stay active; but photo-replacement is a plausible action in the field. Missing this from the audit log is a completeness gap for D-06.

**Fix:** Extend the condition to also capture photo replacement:

```sql
if (NEW.photo is not null and OLD.photo is null)
   or (NEW.photo is not null and OLD.photo is not null and NEW.photo <> OLD.photo) then
  v_action := 'patient_photo';
```
